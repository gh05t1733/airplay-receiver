## Revision v3.3 2026-09-16 (mDNS must go through the running Bonjour daemon)
Verified on disk (not taken on trust): `sc query "Bonjour Service"` = RUNNING; `tasklist` shows
mDNSResponder.exe pid 10956; `netstat -ano | grep :5353` shows pid 10956 on 192.168.1.14:5353 plus three
other PIDs on 0.0.0.0:5353 (i.e. the port is already contended); `dns-sd.exe` (96,104 B) and `dnssd.dll`
(85,864 B) exist in System32; a filesystem search found **no** `dns_sd.h` and no `Bonjour SDK`; VS 18
BuildTools has **no atlmfc** (so ATL/MFC-dependent builds — the SDK's dns-sd CLI, and the msbuild-based
vcpkg mdnsresponder port — are not viable here).
Decisions:
- Advertiser registers through the daemon via dynamically loaded `dnssd.dll` + vendored Apache-2.0
  `dns_sd.h` (apple-oss-distributions/mDNSResponder). Our process must never bind 5353 while a daemon is
  present; hand-rolled responder only on Bonjour-less hosts, where it must own 5353 exclusively.
- vcpkg `mdnsresponder` demoted to optional feature `mdns-vendored`; default Sprint 1 deps = openssl,
  spdlog, catch2 (pure CMake ports) — removes both the FFmpeg and the ATL risk from gate 1.1.
- Gates: 1.2/1.11 verify with the system `dns-sd.exe`; 1.3 additionally proves our PID is not the 5353
  owner; 4.3 + C19 handle the Bonjour runtime dependency for end users (bundle vs prompt; Apple terms).
- R4 rewritten: the flakiness cause is (a) multi-homed adapters and (b) fighting the daemon for 5353.
